## 0. Как читать это ТЗ

Документ описывает интерфейс (фронтенд) системы: экраны, компоненты, состояния, поведение, требования к адаптиву и порядок работ.
Бэкенд, интеграции с почтой, Яндекс Диском и языковыми моделями описываются в отдельном ТЗ. Здесь фиксируется только контракт данных, с которым работает интерфейс.

Приоритет каждого экрана привязан к этапу проекта:
- **Э1**: Этап 1, ядро «запрос → КП» (делаем первым)
- **Э2**: Этап 2, поставщики и контроль
- **Э3**: Этап 3, документы, аналитика, рассылка

Пометка **[УТОЧНИТЬ]** значит: решение принимается после аудита, до этого делаем по допущению из раздела 13.

## 1. Цель интерфейса

Менеджер открывает систему и за 5 секунд видит, что требует его действия. Рутину делает система, человек проверяет и подтверждает.

Три главных сценария, под которые оптимизируется интерфейс:
1. **Проверить и отправить КП**: открыть запрос, сверить распознанные позиции с письмом, поправить, подтвердить отправку. Цель: до 2 минут на типовой запрос.
2. **Разобраться с проблемным запросом**: нет артикула, нет цены, поставщик молчит или отказал.
3. **Руководителю увидеть картину**: сколько запросов, где застряли, какая конверсия.

## 2. Пользователи и роли

| Роль | Что делает | Доступ |
|---|---|---|
| Менеджер | Проверяет запросы и КП, подтверждает отправку, ведет статусы | Запросы, КП, клиенты, поставщики, спецификации |
| Руководитель | Смотрит воронку и аналитику, меняет правила расчета | Все, кроме управления пользователями |

Права проверяются на бэкенде. Интерфейс скрывает недоступные разделы и кнопки, но не является защитой.

## 3. Стек и технические требования

- React 18 + TypeScript (strict) + Vite
- Tailwind CSS + shadcn/ui (Radix) как база компонентов
- TanStack Query для данных, TanStack Table для таблиц, TanStack Router или React Router
- React Hook Form + Zod для форм и валидации
- Моки API на MSW: интерфейс разрабатывается параллельно с бэкендом по контракту из раздела 11
- Иконки: lucide-react
- Даты: date-fns, часовой пояс отображения МСК, формат ДД.ММ.ГГГГ ЧЧ:ММ
- Деньги: форматирование через Intl.NumberFormat, «171 800 ₽», валюта поставщика показывается рядом с рублевой суммой
- Язык интерфейса: русский. Все тексты в одном файле словаря
- Запрещено: Supabase, n8n, Make, конструкторы. Никаких секретов и ключей во фронтенде

Структура:
```
src/
  app/            роутинг, провайдеры, layout
  pages/          экраны
  features/       бизнес-блоки (requests, quotes, suppliers, pricing...)
  components/ui/  базовые компоненты shadcn
  components/     общие компоненты (StatusBadge, ConfidenceBadge...)
  api/            клиент API, типы, хуки TanStack Query
  mocks/          MSW-обработчики и тестовые данные
  lib/            форматирование, утилиты
  i18n/ru.ts      все тексты интерфейса
```

## 4. Дизайн-система

**Тема.** Основная: светлая (менеджер работает с таблицами весь день). Темная: переключатель в профиле.
**Акцент:** #B35A2A (кнопки основного действия, активный пункт меню). **Темные поверхности:** #23303A (сайдбар, шапки таблиц в темной теме). Акцент выносится в CSS-переменную, чтобы при необходимости заменить на цвет клиента.

**Шрифт:** Inter, базовый размер 16 px на телефоне, 14-15 px в плотных таблицах на десктопе.
**Сетка отступов:** 4 px. **Радиусы:** 8 px карточки, 6 px поля.

**Цвета статусов** (всегда цвет + текст, никогда только цвет):

| Смысл | Цвет | Примеры |
|---|---|---|
| Требует действия | янтарный | На проверке, Нужен артикул |
| Ожидание | синий | Ждем поставщика, Ждем клиента |
| Успех | зеленый | КП отправлено, Выигран |
| Проблема | красный | Просрочено, Отказ, Ошибка |
| Нейтрально | серый | Новый, Закрыт |

**Уверенность распознавания** (ConfidenceBadge):
- Высокая (от 0,9): зеленая точка + «Уверенно»
- Средняя (0,7-0,9): янтарная + «Проверьте»
- Низкая (ниже 0,7): красная + «Нужна проверка», строка подсвечена

Пороги выносятся в настройки.

## 7. Экраны подробно

### 7.1 Вход (Э1)
Email + пароль, «Запомнить меня», восстановление пароля по email. Ошибки текстом под полем. После входа: переход на «Сегодня».

### 7.2 Сегодня (Э1)
Главный рабочий экран менеджера.

Блоки сверху вниз:
1. **Требует действия** (счетчики-кнопки, переход в отфильтрованный список): На проверке · Нужен артикул · Ответ поставщика получен · Просрочено
2. **Очередь на проверку**: 5-10 последних запросов со статусом «На проверке», кнопка «Проверить» ведет сразу в карточку
3. **Ожидание**: сколько ждут поставщика и клиента, ближайшие напоминания (Э2)
4. **Мини-статистика дня**: получено запросов, отправлено КП

Пустое состояние: «Все запросы обработаны» + время последней проверки почты.

### 7.3 Входящие запросы (Э1)
**Колонки (десктоп):** № · Дата получения · Клиент · Тема письма · Позиций · Уверенность (худшая по запросу) · Сумма КП · Статус · Ответственный · Обновлено
**Карточка (телефон):** клиент, тема, статус, позиций, сумма, время.

**Фильтры:** статус (мульти), ответственный, клиент, период, «только требует действия», «низкая уверенность».
**Поиск:** по номеру, клиенту, теме, артикулу.
**Сортировка:** по дате (по умолчанию новые сверху), сумме, статусу.
**Пагинация:** серверная, по 50.
**Массовые действия (десктоп):** назначить ответственного, закрыть.

Индикатор «новое» на непрочитанных. Автообновление списка каждые 60 секунд без сброса фильтров и прокрутки.

### 7.4 Карточка запроса (Э1, главный экран системы)

**Шапка:** № запроса, клиент (ссылка на карточку), статус, ответственный, дата, кнопки «Назначить», «Закрыть».

**Зона 1. Письмо клиента**
- Оригинал письма: отправитель, дата, тема, текст (безопасный рендер HTML, без внешних скриптов и картинок до клика «Показать изображения»)
- Вложения: список, скачивание, предпросмотр PDF и изображений
- Подсветка фрагментов текста, из которых распознаны позиции (клик по позиции подсвечивает фрагмент)

**Зона 2. Распознанные позиции** (редактируемая таблица)
Колонки: Артикул · Наименование · Бренд · Кол-во · Ед. · Категория · Цена поставщика (валюта) · Источник цены (прайс / ответ поставщика / вручную) · Пошлина · Цена для клиента · Сумма · Уверенность
- Редактирование в строке, автосохранение с индикатором «Сохранено»
- Добавить позицию вручную, удалить, объединить дубли
- Позиция без артикула: статус строки «Нужен артикул», кнопка «Запросить у клиента» (открывает предпросмотр письма)
- Позиция без цены: «Цена не найдена», кнопка «Запросить у поставщика» (Э1: заглушка «будет в Этапе 2», Э2: работает)
- Под таблицей: итог без пошлины, пошлина, итог, валюта и курс, округление

**Зона 3. Действия и история** (правая колонка / липкая панель на телефоне)
- Главная кнопка по состоянию:
  - есть позиции с низкой уверенностью: «Проверьте позиции» (неактивна отправка, счетчик непроверенных)
  - все проверено: «Сформировать КП»
  - КП сформировано: «Предпросмотр и отправка»
- Лента событий: письмо получено, распознано, правки менеджера, запросы поставщикам, ответы, отправки. Каждое событие с автором (человек или «Система»)

**Правило:** ничего не уходит клиенту или поставщику без явного подтверждения в диалоге с предпросмотром письма.

### 7.5 Редактор и предпросмотр КП (Э1)
- Предпросмотр КП в виде таблицы, как в XLS-шаблоне клиента
- Поля: номер КП, дата, срок действия, условия поставки и оплаты (подставляются из настроек, редактируемые)
- Предпросмотр письма клиенту: кому, копия, тема, текст из шаблона, вложение XLS
- Кнопки: «Скачать XLS», «Отправить клиенту», «Сохранить черновик»
- После отправки: статус «КП отправлено», ссылка на файл на Яндекс Диске, событие в ленте
- Версии КП: при повторной отправке создается v2, прошлые доступны для просмотра

### 7.6 Клиенты (Э1)
Список: название, домен почты, запросов, КП отправлено, выиграно, сумма заказов, последний контакт.
Карточка: реквизиты, контакты, история запросов и КП, статистика (Э3).
Клиенты создаются автоматически из входящих писем по домену, менеджер может объединить дубли.

### 7.7 Прайсы и номенклатура (Э1)
- Список источников: файл на Яндекс Диске, поставщик/бренд, валюта, строк, дата последней синхронизации, статус (ОК / есть ошибки / не обновлялся N дней)
- Кнопка «Синхронизировать сейчас»
- Отчет об импорте: сколько строк загружено, пропущено, почему (нет артикула, некорректная цена)
- Настройка сопоставления колонок для каждого прайса: какая колонка артикул, наименование, цена, валюта
- Поиск по артикулу по всем прайсам: где найден, цена, дата прайса
- Ассортиментная матрица: артикул → категория, ручная правка категории

### 7.8 Настройки: правила расчета (Э1)
- Категории товаров и пошлина по категории (по умолчанию 5% для «Реактивы» и «Лабораторные наборы»)
- Валюты и курсы: источник курса [УТОЧНИТЬ: ЦБ РФ или ручной], надбавка к курсу
- Наценка по категориям или общая [УТОЧНИТЬ]
- Правило округления
- **Калькулятор-проверка:** ввести цену, валюту, категорию и увидеть расчет по шагам. Нужен, чтобы клиент сам проверил формулу на приемке
- Изменения правил логируются в журнал, применяются к новым КП

### 7.9 Настройки: шаблоны (Э1)
- Шаблоны писем: КП клиенту, запрос артикула, запрос поставщику (EN), напоминание поставщику, отказ клиенту, follow-up клиенту
- Переменные в шаблонах вставляются из списка ({клиент}, {номер_КП}, {артикулы}), предпросмотр с тестовыми данными
- Шаблоны документов: загрузка XLS-шаблона КП и спецификации, проверка, что все обязательные поля найдены

### 7.10 Пользователи и роли (Э1)
Список, приглашение по email, роль, блокировка, последний вход.

### 7.11 Журнал действий (Э1)
Таблица: время, пользователь или «Система», действие, объект (ссылка), подробности. Фильтры по пользователю, типу действия, периоду. Только чтение.

### 7.12 Поставщики (Э2)
- Список: название, email, бренды, запросов, среднее время ответа, доля отказов
- Карточка: контакты, бренды, история запросов и ответов по цепочкам
- Вкладка «Запросы поставщикам»: артикулы, дата отправки, статус (Отправлен / Напоминание отправлено / Ответ получен / Отказ / Просрочен), дней в ожидании
- Разобранный ответ поставщика: цена, срок, условия, отказ, с уверенностью и ссылкой на оригинал письма. Менеджер подтверждает, данные уходят в позиции запроса

### 7.13 Воронка (Э2)
Канбан по статусам запроса (раздел 9). Карточка: клиент, сумма, дней в статусе, ответственный.
- Перетаскивание только между разрешенными статусами, недопустимый переход: подсказка почему
- Колонки с просрочкой подсвечены
- На телефоне: вкладки-статусы со списком, без перетаскивания, смена статуса через меню карточки

### 7.14 Спецификации (Э3)
Мастер из 3 шагов:
1. Выбор PO (загрузка файлов или выбор из писем)
2. Свод: объединенные позиции, суммы количеств, расхождения подсвечены (разные цены на один артикул)
3. Предпросмотр по шаблону с факсимиле подписи и печати, скачать, отправить
Список созданных спецификаций с версиями.

### 7.15 Аналитика (Э3)
Период + фильтр по менеджеру.
- KPI-карточки: запросов, КП отправлено, конверсия КП в заказ, среднее время обработки запроса, сумма заказов
- Графики: запросы и КП по неделям, воронка статусов, топ-20 повторяющихся артикулов, топ клиентов по запросам и по сумме
- Выгрузка любой таблицы в XLSX

### 7.16 Рассылки NEWS (Э3)
Список рассылок: тема, дата, получателей, отправлено, ошибок. Карточка: предпросмотр письма, список получателей из файла, статус отправки по каждому, пауза и отмена очереди.

### 7.17 Подключения (Э3)
Статус и проверка: почтовый ящик, папки (запросы, NEWS), Яндекс Диск, языковая модель, поиск. Кнопка «Проверить подключение», последняя ошибка текстом. Секреты не показываются, только «подключено» и дата.

## 9. Статусы

**Запрос:**
Новый → Распознан → (Нужен артикул) → (Ждем поставщика) → На проверке → КП отправлено → Ждем ответа клиента → Запрошен счет / спецификация → Выигран / Проигран / Закрыт

**Запрос поставщику (Э2):** Отправлен → Напоминание отправлено → Ответ получен / Отказ / Просрочен

**КП:** Черновик → Отправлено → Просмотрено клиентом [УТОЧНИТЬ, если возможно отследить] → Устарело

Карта разрешенных переходов приходит с бэкенда, интерфейс ее не зашивает.

## 10. Состояния, ошибки, уведомления

Для каждого экрана обязательны 4 состояния: загрузка (скелетон), пусто (с подсказкой, что делать), ошибка (текст + «Повторить»), данные.

- Ошибки сети: тост «Нет соединения, изменения сохранятся после восстановления» для автосохранения, блокирующий диалог для отправки
- Ошибки валидации: под полем, человеческим языком
- Уведомления в шапке: ответ поставщика получен, просрочка, ошибка синхронизации прайса, ошибка отправки письма
- Опасные действия (отправка, закрытие, удаление): диалог подтверждения
- Отмена последнего действия (undo) для удаления позиции и смены статуса: 5 секунд

## 11. Контракт данных (минимум для интерфейса)

Интерфейс работает через REST API. Точные схемы фиксируются в OpenAPI бэкенда, ниже минимальные сущности.

```ts
type RequestStatus = 'new'|'parsed'|'need_article'|'waiting_supplier'
  |'review'|'quote_sent'|'waiting_client'|'invoice_requested'
  |'won'|'lost'|'closed';

interface InboundRequest {
  id: string; number: number; receivedAt: string;
  client: { id: string; name: string };
  subject: string; status: RequestStatus;
  assignee?: { id: string; name: string };
  positionsCount: number; minConfidence: number;
  quoteTotalRub?: number; updatedAt: string;
}

interface Position {
  id: string; article?: string; name: string; brand?: string;
  qty: number; unit: string; category?: string;
  supplierPrice?: number; supplierCurrency?: string;
  priceSource?: 'pricelist'|'supplier_reply'|'manual';
  dutyPct: number; clientPriceRub?: number; totalRub?: number;
  confidence: number; reviewed: boolean;
  sourceSpan?: { start: number; end: number };
}

interface Quote {
  id: string; requestId: string; version: number;
  status: 'draft'|'sent'|'outdated';
  totalRub: number; fileUrl?: string; sentAt?: string;
}

interface ActivityEvent {
  id: string; at: string; actor: { type: 'user'|'system'; name: string };
  action: string; details?: Record<string, unknown>;
}
```

Основные эндпоинты: `GET /requests`, `GET /requests/:id`, `PATCH /requests/:id`, `PUT /requests/:id/positions`, `POST /requests/:id/quote`, `POST /quotes/:id/send`, `GET /pricelists`, `POST /pricelists/:id/sync`, `GET /pricing-rules`, `PUT /pricing-rules`, `POST /pricing-rules/preview`, `GET /activity`.

Пока бэкенд не готов, все ответы отдаются из MSW-моков с реалистичными данными: 30 запросов во всех статусах, позиции с разной уверенностью, 3 прайса, 5 клиентов.

## 15. Порядок работ

Работа идет по стадиям, переход только после проверки предыдущей:
1. **Explore:** прочитать ТЗ и смету, задать вопросы одним списком
2. **Specify:** Task Brief по Э1 (экраны, компоненты, критерии приемки) → согласование с Никитой
3. **Design:** каркас + карточка запроса на 390 px и 1440 px в коде на моках → согласование
4. **Implement:** остальные экраны Э1
5. **Verify:** проверка по Definition of Done
6. **Release:** деплой на тестовый стенд neeklo.studio, демо
7. **Completion Report**

Классы изменений при доработках:
- T0: текст и опечатки
- T1: стили, отступы, цвета
- T2: новый элемент или поле на существующем экране
- T3: новый экран или изменение сценария
- T4: изменение контракта API, ролей или инфраструктуры

T0-T1 делаются сразу, T2 с отметкой в журнале задач, T3-T4 только после согласования и оценки.
